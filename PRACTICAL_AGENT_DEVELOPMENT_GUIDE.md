# Часть 1: Проектирование агента

## Введение

Большинство проектов по созданию AI-агентов начинаются неправильно — с написания промпта. Это приводит к хаотичному развитию, когда каждая новая задача требует переписывания системных инструкций, а качество ответов нестабильно.

**Правильный подход:** начинать с проектирования, как при разработке любой сложной системы.

Эта часть посвящена **фазе проектирования** — анализу требований, определению границ и принятию архитектурных решений **до** написания первой строки промпта.

## 1.2 Определение доменов компетенций

### Концепция

**Домен** — это область знаний и навыков, в которой агент должен быть компетентен. Чётко определённые домены позволяют:
- Структурировать знания агента
- Направлять запросы к релевантным инструкциям
- Измерять качество в каждой области отдельно
- Постепенно расширять компетенции

**Ключевое открытие:** Попытка создать "универсального" агента без доменной структуры приводит к размытым, поверхностным ответам. Лучше иметь агента-эксперта в 3-5 доменах, чем посредственного "во всём".

## 1.3 Архитектурные решения

> **⚠️ ВАЖНО: System-Reminder Problem (v1.2.0, GAP-ARCH-002)**
>
> Claude Code CLI оборачивает весь контент из `claudeMd` (CLAUDE.md, rules/, modules/) в тег `<system-reminder>may or may not be relevant</system-reminder>`, что может привести к игнорированию критичных правил.
>
> **Решение:** 3-tier priority override architecture:
> - **TIER 1:** CORE_INSTRUCTIONS.md (52 lines) → injected via `--append-system-prompt` (PRIORITY 2, bypasses reminder)
> - **TIER 2:** claude-wrapper → `alias claude='claude-wrapper'` (auto-loads TIER 1)
> - **TIER 3:** rules/ (7 files, auto-loaded, PRIORITY 3 with reminder)
>
> Критичные правила (routing, git checks, anti-hallucination) размещаются в TIER 1.
> Детальные процедуры и примеры — в TIER 3 (rules/).
>
> **Документация:** `docs/SYSTEM_REMINDER_BYPASS.md`, статья Appendix L
> **Статус:** ✅ Resolved (v3.5.0, 2026-01-29)

### Концепция

На этом этапе принимаются ключевые архитектурные решения, которые определят структуру всей системы. Изменить эти решения позже будет дорого, поэтому важно продумать их тщательно.

**Архитектурный принцип:** Модульность важнее краткости. Лучше иметь 5 хорошо структурированных модулей, чем один монолитный промпт на 10000 токенов.

# Часть 2: Core Identity

## Введение

**Core Identity** — это неизменное ядро вашего агента. Это первое, что загружается в контекст, и последнее, что должно меняться. Хорошо спроектированное ядро обеспечивает:

- **Консистентность** — агент ведёт себя предсказуемо
- **Безопасность** — границы чётко определены
- **Эффективность** — ядро кэшируется, снижая latency

**Ключевое открытие:** Большинство проблем с AI-агентами (галлюцинации, непредсказуемость, выход за границы) решаются на уровне Core Identity, а не добавлением новых инструкций.

---

## 2.1 Определение роли и миссии

### Концепция

Роль — это не просто название ("ты — ассистент"). Роль определяет:
- **Кем** является агент (идентичность)
- **Что** он делает (функция)
- **Как** он работает (режим)
- **Для кого** он работает (отношения)

**Антипаттерн:** "Ты — полезный ассистент, который помогает с любыми задачами"
**Правильно:** Чёткое, ограниченное определение с явными границами

# Часть 3: Когнитивная архитектура

## Введение

**Когнитивная архитектура** — это то, КАК агент думает. В Части 2 мы определили WHAT (что агент делает) и WHO (кем является). Теперь детализируем HOW (как принимает решения).

Хорошо спроектированная когнитивная архитектура обеспечивает:
- **Консистентность** — одинаковые задачи решаются одинаково
- **Трассируемость** — можно понять, почему принято решение
- **Улучшаемость** — можно оптимизировать отдельные этапы

---

## 3.1 Роутинг запросов

### Концепция

**Роутинг** — это механизм направления запросов к соответствующим знаниям/модулям. Без роутинга модульная архитектура бесполезна — агент не знает, какой модуль применить.

**Ключевое открытие:** Роутинг на основе ключевых слов работает в 80% случаев. Для оставшихся 20% нужен семантический анализ или уточнение.

## 3.2 Декомпозиция задач

### Концепция

**Декомпозиция** — разбиение сложной задачи на атомарные подзадачи. Это критически важно для:
- Снижения ошибок (проще проверить маленькие шаги)

- Трассируемости (понятно, на каком этапе что-то пошло не так)

# Часть 4: Модульная система

## Введение

**Модульная система** — это способ организации знаний агента по доменам. Вместо одного гигантского промпта создаются независимые модули, загружаемые по необходимости.

**Преимущества модульности:**
- **Масштабируемость** — новые домены добавляются без переписывания всего
- **Кэширование** — стабильные модули кэшируются, снижая latency
- **Тестируемость** — каждый модуль можно тестировать отдельно
- **Версионирование** — разные версии модулей для разных сценариев

# Часть 5: Gap Management

## Введение

**Gap Management** — система обнаружения и устранения пробелов в конфигурации агента. Это ключевой механизм **непрерывного улучшения**.

**Ключевое открытие:** Без формализованной системы отслеживания пробелов:
- Одни и те же проблемы возникают повторно
- Нет приоритизации улучшений
- Невозможно измерить прогресс

---

## 5.1 Обнаружение пробелов (Gap Detection)

### Концепция

**Gap (пробел)** — это недостаток в конфигурации агента:
- Отсутствующая инструкция
- Неполное покрытие сценария
- Устаревшая информация
- Некорректное поведение

**Источники обнаружения:**
1. **Пользователь** — явно указывает на проблему
2. **Агент** — обнаруживает в процессе работы
3. **Метрики** — аномалии в показателях
4. **Аудит** — систематическая проверка

# Часть 6: Операционные протоколы

## Введение

**Операционные протоколы** — это формализованные процедуры для управления жизненным циклом агента. Без протоколов:
- Изменения вносятся хаотично
- Нет процесса review и approval
- Накапливается технический долг

**Ключевое открытие:** Агент — это живая система, требующая регулярного обслуживания. Протоколы превращают хаос в управляемый процесс.

## 6.5 Создание новых протоколов **[НАША РАЗРАБОТКА]**

- **Атомарным** — одна чётко определённая функция

- **Интегрированным** — связан с GAPS.md и changelog

# Часть 7: Библиотека примеров

## Введение

**Few-shot Examples** — эталонные пары запрос-ответ, демонстрирующие желаемое поведение агента. Это один из самых эффективных способов улучшения качества:

- **+20-40%** к точности на сложных задачах
- Калибровка стиля и формата
- Демонстрация edge cases

**Ключевое открытие:** 3-5 качественных примеров на домен эффективнее, чем 20 посредственных. Качество > количество.

# Часть 8: Оценка и метрики

## Введение

**Оценка (Evaluation)** — систематическое измерение качества агента. Без метрик:
- Невозможно понять, улучшается ли агент
- Нельзя сравнить разные версии
- Оптимизация происходит "вслепую"

**Ключевое открытие:** Субъективная оценка ("кажется, стало лучше") ненадёжна. Нужны объективные, воспроизводимые метрики.

---

## 8.1 Ключевые метрики

### Концепция

# Часть 9: Инструментальная интеграция

## Введение

**Инструменты (Tools)** расширяют возможности агента за пределы генерации текста:
- Выполнение команд
- Чтение/запись файлов
- API вызовы
- Взаимодействие с внешними системами

**Ключевое открытие:** Качество интеграции инструментов определяет полезность агента для реальных задач. Агент без инструментов — это просто чат-бот.
